# Правила работы с этим репозиторием

Здесь живут рекламные страницы школы мотокросса ZRT. Всё, что лежит в `site/`,
публикуется на **https://adv.zrt-school.ru**.

Стек намеренно примитивный: обычные HTML, CSS и JS. Ни сборки, ни npm-зависимостей,
ни бэкенда. Страницу можно открыть двойным кликом из `site/` и увидеть ровно то,
что увидит клиент.

Задачи сюда ставит маркетолог обычными словами («сделай страницу под рекламу зимнего
интенсива»). Ниже — как их выполнять.

## Железные правила

1. **Публикуется только каталог `site/`.** Всё остальное (`templates/`, `docs/`,
   `scripts/`, `.github/`) на сервер не уезжает. Нужно, чтобы файл увидел клиент —
   значит, он лежит в `site/`.
   Отдельно: `index.html` **в корне репозитория** — не страница сайта, а заглушка,
   которая уводит со старого адреса `sergeyov777.github.io/zrt-landing` на боевой.
   Контент правится в `site/index.html`, корневой файл не трогать.
2. **Никаких сборщиков и зависимостей.** Ни React, ни Tailwind, ни npm-пакетов,
   ни шага build. Только статика.
3. **Перед тем как открывать pull request — прогнать `node scripts/check-site.mjs`.**
   Проверка не должна давать ни одной строки с `✖`. Ровно эта же проверка стоит
   в CI и не пропустит выкат.
4. **Работать в отдельной ветке и открывать pull request.** Прямой push в `main`
   не делать: merge = мгновенная публикация на боевой сайт, решение о ней принимает
   человек.
5. **Один pull request — одна задача.** Одна страница или одна правка, а не «заодно
   поправил ещё пять мест».
6. **Не менять `.github/workflows/site.yml` и `scripts/check-site.mjs`** без явной
   просьбы: это механика публикации, а не контент.
7. **Никаких ключей, паролей и токенов в репозитории.** Их здесь нет и быть не должно.

## Как добавить новую рекламную страницу

1. Скопировать болванку: `cp templates/page.html site/<slug>.html`.
   `<slug>` — латиницей, строчными, через дефис: `winter-intensive`, `kids-camp`.
   Адрес страницы получится `https://adv.zrt-school.ru/<slug>`.
2. Заполнить `<title>`, `<meta name="description">` и тексты. Все метки
   `ЗАПОЛНИТЬ`, `ЗАГОЛОВОК СТРАНИЦЫ` и подобные обязаны исчезнуть — проверка
   валит выкат, если находит их.
3. Готовые блоки не изобретать, а копировать из `site/index.html`: `.features`
   (преимущества), `.pricing` (цены), `.testimonials` (отзывы), `.photo-gallery`
   (фотогалерея), `.motorcycles` (мототехника). Они уже свёрстаны и адаптивны.
4. Прогнать `node scripts/check-site.mjs`, открыть pull request.

## Как поменять текст, цены или акцию на существующей странице

Править нужный `.html` в `site/`. Стили и скрипты общие: `site/styles-improved.css`
и `site/script-improved.js` действуют на всех страницах — правка там меняет
поведение всего сайта, поэтому делать это только когда задача действительно
общая для всех страниц.

## Картинки

- Класть в `site/assets/`, ссылаться относительным путём: `assets/foto.jpg`.
- Ссылки на `http://` запрещены — браузер заблокирует их на https-странице,
  проверка это ловит.
- Фотографии на главной сейчас грузятся с внешнего `static.tildacdn.com` (наследие
  старой версии сайта). Для новых страниц так не делать: складывать файлы в
  `site/assets/`.

## Чего делать нельзя

- Переименовывать или удалять `site/index.html`, `site/styles-improved.css`,
  `site/script-improved.js`. Сервер отказывается публиковать выкат без `index.html`.
- Выбрасывать со страницы форму `id="contactForm"` или модальное окно
  `id="successModal"` — общий `script-improved.js` рассчитывает на эту разметку
  и без неё ломается на всей странице.
- Подключать внешние скрипты (аналитика, пиксели, чаты) по своей инициативе.
  Только если об этом попросили явно.
- Использовать путь `/_preview/` — он служебный, там лежат черновики.

## Важное ограничение, о котором надо предупреждать

**Форма заявки никуда не отправляет данные.** В `site/script-improved.js`
функция `handleSubmit` (около строки 285) только показывает окно «Заявка успешно
отправлена» через `setTimeout` — запроса на сервер нет. То есть заявки клиентов
сейчас **теряются**.

Если задача связана с заявками, лидами, подключением CRM или аналитики — не делать
вид, что форма работает. Сначала сказать об этом человеку: нужен бэкенд-приёмник
(например, отправка в amoCRM), это отдельная работа, и делает её разработчик.

## Как правки попадают на сайт

- Открыт pull request → GitHub автоматически проверяет страницы и выкладывает
  **черновик** на `https://adv.zrt-school.ru/_preview/pr-<номер>/`, ссылку пишет
  комментарием в PR. Черновик закрыт от поисковиков, живёт 14 дней.
- Человек нажал «Merge pull request» → те же проверки и публикация на боевой адрес.
  Занимает меньше минуты, кэш HTML отключён — обновление видно сразу.
- Откат — `git revert` нужного коммита и merge (подробнее в `docs/DEPLOY.md`).

Сервером и ssh управлять не нужно и невозможно: ключ выката есть только у GitHub
Actions и умеет ровно одну операцию — принять архив сайта.
